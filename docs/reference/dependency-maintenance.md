# Dependency Maintenance Report

This reference helps the maintainer review selected dependency versions and
upstream activity. The canonical observation is
[`dependency-maintenance.json`](dependency-maintenance.json), generated by
`scripts/dependency_maintenance.py`. It covers every component in the
[source inventory](dependency-inventory.json) and each declaration in the
[image inventory](dependency-image-inventory.json). It does not certify
maintenance health, detect vulnerabilities or approve dependency admission.

## Reading The Report

`as_of` is the UTC observation time. Component rows preserve ecosystem, exact
selected version and graph origins. Repository records preserve the requested
identity and GitHub's observed canonical identity, including redirects/renames.
The source inventory and all current generator/manifest/fixture inputs are
hashed; changed inputs require a fresh report.
Counts describe selected package/module versions, so several rows may share
one repository. Go graphs include available modules beyond those linked into
any particular binary.

| Review signal | Trigger |
| --- | --- |
| `selected-version-365-days-old` | Selected version timestamp is at least 365 days old. |
| `repository-no-push-730-days` | GitHub's recorded last push is at least 730 days old. |
| `repository-archived` | GitHub reports the public repository archived. |
| `repository-disabled` | GitHub reports the public repository disabled. |
| `package-deprecated` | The selected npm version has a nonempty deprecation notice. |
| `timestamp-in-future` | A source timestamp is more than one day after the observation time. |

These thresholds identify review candidates. An old stable release may still
serve its purpose, and a recent push does not prove active support or security.
A push timestamp describes repository activity across refs, not an assessment
of the selected version. No signal automatically removes or replaces a package.

`status: review` means a listed signal exists. `unknown` means no listed signal
was observed but metadata is missing. `no-listed-signal` means the available
fields meet neither condition; it is not a health or safety verdict. Rows can
have both review signals and metadata gaps. The top-level summary counts both.

Fixture payload hashes are not published dependency versions. Where available,
the report records their pinned source commit date separately and does not
label it the payload's release date. Action pins use their selected commit date.
Image rows preserve operator choices and missing dates; mutable registry tags
also carry `mutable-image-reference`. They do not infer the age of an image
from an unrelated GitHub release or extend coverage to every contained package.

For example, list component review candidates with their gaps:

```sh
jq '.components[] | select(.status == "review") | {ecosystem, name, version, review_signals, metadata_gaps}' \
  docs/reference/dependency-maintenance.json
```

Review the concrete upstream state, replacement cost, relevant advisories and
[selection/removal criteria](dependency-policy.md#selection-and-removal).
Preserve pinned historical fixture/release evidence when planning an update.

## Metadata Sources And Limits

- Go version timestamps come from the verified inventory. For non-GitHub module
  paths and missing dates, an exact-version Go proxy `.info` observation supplies
  origin metadata. Only observed GitHub origin URLs are mapped to GitHub;
  other hosts remain unmapped. Version/time disagreements fail collection.
- npm metadata comes from each exact selected version in its public registry
  document, including its version timestamp, declared source repository and
  deprecation state. Large registry documents remain explicit `over-budget`
  gaps. Deprecation prose is omitted from public output.
- PyPI's exact-version metadata supplies declared repository links; its version
  timestamp remains bound to the source inventory's artifact observation.
- Fixture and Action source repositories/commits come from the inventory.
  Helm/oasdiff release dates use their named public GitHub releases. GitHub
  repository metadata and pinned commit dates are fetched in bounded batches.

Provider metadata is an observation, not proof that repository activity
supports a particular release. Repository declaration/redirect changes are not
authorization to change source pins. Unsupported hosts, missing repositories,
missing timestamps, unresolved image choices and over-budget documents stay
visible. These gaps require judgment; they do not become empty passing data.
Metadata digests identify canonical parsed values, including local gap-status
objects for unavailable documents; they do not authenticate publisher content.

Requests use fixed HTTPS providers with no inherited proxy settings or registry
credentials. GitHub CLI authentication is needed for public GraphQL queries;
only read queries are constructed. Provider timeouts, authentication/rate-limit
failures, malformed identities and unexpected responses fail generation.
Expected not-found responses remain gaps. JSON responses are limited to 4 MiB;
GitHub repository count and batch sizes are bounded. No package install,
entrypoint, build script or dependency executable runs. Public output omits
provider contact fields, raw deprecation prose, tokens and raw error bodies.

## Refresh And Validate

```sh
"$HOME/.local/bin/codex-ramgate" 1 -- make dependency-maintenance-generate
make dependency-maintenance-check
```

The generation command performs serial metadata reads; use a larger RAM
reservation if increasing its bounds. The verified local run used a 512 MiB
cgroup memory limit. Existing report files are replaced only with
`--replace` and the matching schema. Symlinks, unrelated files and concurrent
source/output edits fail without overwriting the owner's changes.

`make dependency-maintenance-check` runs isolated regressions and verifies
input hashes, complete row coverage and deterministic signals offline. It is
included in `make docs-check`, which also compiles Go tools and therefore needs
a suitable RAM reservation. Offline checks recompute signals at the saved
`as_of`; they do not refresh provider state or advance an old observation date.
EVY-1407's trusted PR admission and required final gates remain separate work.
