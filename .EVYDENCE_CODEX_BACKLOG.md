This backlog is the execution handoff for taking Evydence from a useful
production-oriented prerelease to a credible 9/10 project across dependency
worthiness, architecture, tests, documentation, open-source trust, ecosystem
fit, feature completeness, and API design.

It is intentionally strict. Passing repository-local checks is necessary but
is not sufficient for the external-review, repository-settings, and real-user
evidence tickets. Codex must not fabricate external evidence or mark those
tickets complete without verifiable proof.

## Status Syntax

- `[ ]` means incomplete.
- `[x]` means complete and fully verified.
- An epic may be changed to `[x]` only after every child ticket is `[x]` and
  the epic exit criteria pass.
- A ticket may be changed to `[x]` only after all implementation steps,
  acceptance criteria, validation commands, documentation updates, and
  migration or compatibility obligations are complete.
- Partial implementation does not justify `[x]`.
- Blocked tickets stay `[ ]` and receive a short `Blocked:` note with the
  exact missing evidence or prerequisite.

## Codex Operating Contract

1. Revalidate the repository head before starting. If `master` no longer
   points to the baseline commit, inspect the intervening commits, update the
   baseline section in this file, and reconcile completed or obsolete work.
   Never assume the backlog still matches changed code.

2. Work in dependency order unless a ticket explicitly has no dependency.
   Do not start a ticket while a listed dependency is incomplete.

3. Work on one ticket at a time. Keep the working tree clean between
   tickets. Do not combine unrelated tickets.

4. Use Conventional Commits for every commit:

   ```text
   <type>(<scope>): <imperative summary> (<ticket-id>)
   ```

   Allowed types:

   ```text
   feat
   fix
   refactor
   perf
   test
   docs
   build
   ci
   chore
   revert
   ```

   Examples:

   ```text
   fix(verification): reject metadata-only cosign checks (EVY-101)
   refactor(persistence): add transaction unit of work (EVY-203)
   test(idempotency): cover concurrent duplicate requests (EVY-303)
   docs(api): document endpoint stability levels (EVY-701)
   ci(release): enforce changelog and API diff gates (EVY-1408)
   ```

   Use `!` and a `BREAKING CHANGE:` footer for intentional breaking changes.
   Breaking changes must also include migration notes, OpenAPI updates, SDK
   updates, examples, and changelog entries in the same ticket.

5. Commit after every completed ticket or meaningful, independently valid
   subtask. Do not create vague `WIP` commits. Every intermediate commit must
   build and pass the relevant focused tests. If a ticket is too large for
   one coherent commit, split it into explicit sub-tickets in this backlog
   before implementing it.

6. The final implementation commit for a ticket must update the ticket
   checkbox to `[x]`. Add a `Completion evidence:` line below the ticket with
   the exact checks run. Record the implementation commit SHA in the repository
   tracking record after that commit exists; a commit cannot contain its own
   final SHA. If the ticket used several meaningful commits, list all of them.

7. Preserve existing code and comments outside the explicitly changed area.
   Use ASCII characters in comments and documentation. Keep Go code formatted
   with `gofmt`, keep code lines near 80 characters where practical, and
   avoid clever abstractions without a measured need.

8. Never weaken validation, tenant isolation, append-only history, safe error
   handling, redaction, or non-claim language merely to make a test pass.

9. Do not add claims that Evydence proves legal compliance, certification,
   complete SBOM coverage, authoritative vulnerability truth, regulator
   acceptance, auditor acceptance, or guaranteed release security.

10. Do not add dependencies casually. For each new dependency, record:
    maintainer activity, license, release cadence, vulnerability history,
    transitive footprint, why the standard library is insufficient, and the
    fallback or replacement strategy.

11. Never store or commit credentials, customer data, raw private evidence,
    signing keys, database URLs, access tokens, package secrets, or provider
    credentials. Use sanitized fixtures.

12. If an external or maintainer-owned ticket cannot be completed by Codex,
    Codex may prepare scripts, templates, checklists, and evidence locations,
    but must leave the ticket `[ ]` until the named owner supplies proof.

## Validation Matrix

Run the narrowest useful checks during development and the full required gate
before checking the ticket complete.

| Change type               | Minimum required checks                                                                     |
|---------------------------|---------------------------------------------------------------------------------------------|
| Documentation only        | `make docs-check`                                                                           |
| Go implementation         | `go test ./...`, `make fast-check`                                                          |
| HTTP or OpenAPI           | `make openapi-check`, `make sdk-check`, route tests                                         |
| Persistence or migrations | PostgreSQL integration tests, `make migration-compatibility-check`, `make production-check` |
| Concurrency               | focused stress test, `go test -race ./...`, `make production-check`                         |
| Parser or archive         | fixture corpus, fuzz seeds, negative tests, `make production-check`                         |
| Security or cryptography  | focused vectors, `make release-check`, `gosec`, `govulncheck`, CodeQL-compatible tests      |
| Deployment                | Compose and Helm checks, black-box binary or image test                                     |
| Release                   | every command in `docs/reference/stable-v0.1.0-exit-criteria.md`                            |

If a required dependency such as PostgreSQL, MinIO, Docker, or release signing
material is unavailable, do not mark the ticket complete. Record the blocker.

## Ticket Definition Of Done

Every ticket is done only when:

- the implementation is complete and intentionally scoped;
- positive, negative, boundary, and failure-path tests exist;
- race-sensitive behavior has race or stress coverage;
- public API, OpenAPI, SDKs, examples, migrations, and docs are aligned;
- user-visible changes appear in `CHANGELOG.md`;
- no generated file is stale;
- relevant local and CI-equivalent checks pass;
- the completion commit uses Conventional Commits;
- the ticket checkbox is `[x]`;
- completion evidence is recorded;
- the working tree is clean.

## Epic Definition Of Done

Every epic is done only when:

- all child tickets are `[x]`;
- the epic exit criteria pass;
- no open P0 or P1 defect remains in the epic area;
- the objective scorecard is updated with repository evidence;
- documentation states remaining limitations honestly;
- the final epic commit is conventional and records the validation evidence.

## Baseline Blockers This Backlog Must Close

These are known at the baseline commit and should be treated as concrete
starting evidence, not speculative concerns:

1. `internal/app/integrity_runtime.go` can label metadata-presence checks
   as successful Cosign verification without cryptographic verification.
2. Object-retention verification can report a positive status without a
   provider-backed verifier.
3. `internal/app/ledger.go` and related services commonly mutate process
   maps before durable persistence succeeds.
4. `internal/app/ledger.go` uses check-then-act idempotency that permits
   concurrent duplicate side effects.
5. `internal/app/state.go` can silently normalize to empty state when a
   clone marshal or unmarshal fails.
6. Object bytes can be written before database metadata commits, without
   a complete staged/finalized reconciliation protocol.
7. Existing parsers model reduced subsets and can reject valid standard
   extension fields.
8. HTTP request buffering and application upload limits are inconsistent.
9. `sdk/go/evydence/client.go` is an unpublished, partial, untyped wrapper
   with no production constructor or default timeout.
10. SDK fields including release `project_id` and artifact `release_id`
    do not match fields consumed by current server handlers.
11. `Ledger` is a process-wide mutable aggregate with a global mutex and
    broad resource ownership.
12. Readiness reports configured interfaces rather than live dependency
    health, and `/v1/version` reports `dev`.
13. `CHANGELOG.md` and current public release truth are stale relative to
    `master`.
14. Governance, release authority, security response, and continuity
    remain concentrated in one maintainer account.

- a migration cannot be proven against every supported release state;
- a test is flaky or requires timing increases to pass;
- an external standard or cryptographic behavior is uncertain and no
  authoritative specification or maintained implementation has been
  selected;
- a change would weaken tenant isolation, append-only history, redaction,
  verification, or supported deployment safety;
- a release or security claim would exceed evidence;
- required live PostgreSQL, object-store, provider, signing, or release
  verification cannot be executed;
- external settings or reviews are unavailable.

Record the blocker precisely. Do not guess, silently downgrade the test,
or mark the ticket complete.
